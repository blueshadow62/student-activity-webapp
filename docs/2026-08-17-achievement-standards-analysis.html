성취기준 연동 — 분석 단계 정리

코드 변경 없음 지금까지 조사한 내용만 정리한 문서다. 결정이 필요한 지점은 맨 아래 확인이 필요한 질문에 모았다.

1. 지금 웹앱 구조 (관련 부분만)

1-1. 과목은 지금 자유 입력 텍스트다

담당 신청 화면(Index.html #requestSubject)은 그냥 텍스트 입력창이다. 정해진 목록이 없고, Code.gs의 DEFAULT_SUBJECTS는 "학년 → 과목" 힌트 한 벌만 저장한다(지금은 2학년→문학, 3학년→실용국어 두 줄뿐 — 이 학교 국어 교사 개인 설정 흔적으로 보인다). 학교 전체 교과 목록이라는 개념 자체가 없다.

1-2. 학생 활동 기록 화면에는 성취기준을 넣을 자리가 없다

recordEditor(활동 기록 입력 카드)는 구분 · 역량 · 내용메모 세 칸뿐이다. 성취기준 칼럼은 없다. 다만 이 앱은 시트 열을 나중에 추가한 전례가 있다 — 담당키 열을 v8.4에서 추가하면서 기존 시트는 접속 시 열이 자동으로 늘어나고, 그 전 기록은 빈 칸으로 남기는 방식을 이미 썼다(README 참고). 성취기준 열도 같은 방식으로 얹을 수 있다는 뜻이다.

1-3. "학교급(중/고)" 설정 자체가 없다

InstallationSetup.gs의 최초 설치 화면은 학교명만 받는다. 중학교/고등학교 구분을 저장하는 Script Property가 없다. 사용자가 요청한 "관리자가 설치 시 학교급을 고른다"는 지금 존재하지 않는 단계를 새로 만드는 일이다.

1-4. 데이터가 사는 곳: 구글시트뿐, 외부 네트워크 호출 없음

이 앱은 Google Apps Script + Google Sheets 조합이고, appsscript.json의 oauthScopes는 spreadsheets · drive · userinfo.email · script.send_mail 넷뿐이다. 외부 URL을 서버에서 직접 불러오는 UrlFetchApp에 필요한 script.external_request 권한이 없다. 업데이트 알림 기능을 만들 때도 "서버에서 깃허브를 읽으면 이 권한이 필요해지고, 그러면 이미 쓰고 있는 교사 전원이 재동의 화면을 다시 보게 된다"는 이유로 일부러 브라우저(클라이언트)에서만 확인하도록 설계했다(README "업데이트" 항목). 이 프로젝트는 새 권한 추가에 이미 한 번 신중하게 피해간 전례가 있다.

2. 외부 저장소(DECK6/korean-secondary-learning-map) 조사 결과

항목내용
정체2022 개정 교육과정 중·고 전체를 다루는 학습 온톨로지 프로젝트. 버전 v0.5.0-candidate — 아직 정식(1.0) 릴리스가 아니다.
배포 형식정규화된 JSON 파일 여러 개(data/kr/middle/*.json, data/kr/high/*.json) + RDF/OWL 온톨로지. 공개 API는 없다. 로컬에서 bun으로 빌드해 웹 UI로 보는 구조.
라이선스저장소 코드·가공 데이터는 MIT. 단, 교육과정 고시문 원문 자체의 저작권은 포함하지 않는다고 명시.
규모중학교 24개 과목 · 성취기준 714개. 고등학교 759개 과목 · 성취기준 50,749개(그중 일반고 공통·선택 과목이 3,124개, 특성화·전문교과가 47,625개).

⚠ 가장 중요한 문제: "성취기준 문구"가 공식 원문이 아닐 수 있다

docs/data-contract.md의 성취기준 스키마 예시를 보면 성취기준 객체는 summary(요약문), summaryKind, officialTextIncluded 필드를 갖는다. 예시 값은:

"summary": "저장소 작성 요약",
"summaryKind": "mechanical-derivative",
"officialTextIncluded": false

즉 이 저장소가 들고 있는 문구는 공식 고시문 원문이 아니라 저장소 제작자가 기계적으로 만든 요약/파생 문구일 수 있고, 원문 포함 여부는 레코드마다 officialTextIncluded true/false로 갈릴 수 있다(전부 확인은 못 했다 — 실제 standards.json 레코드 표본을 더 봐야 어느 비율이 원문 포함인지 알 수 있다). 학생부·활동기록에 쓰는 성취기준은 코드와 문구가 정확히 일치해야 의미가 있는 자료라, 파생 요약문을 그대로 드롭다운에 노출하면 교사가 실제와 다른 문구를 고를 위험이 있다.

데이터 성숙도: 전체가 아직 "candidate"

reviewStatus: "candidate"가 기본값이고, inventory-report.json의 reviewRecords도 중/고 각각 1건뿐이다. 검증이 아직 충분히 진행되지 않은 초기 버전 데이터라는 뜻이다.

고등학교 데이터가 매우 크다 (5만 건 이상)

전문교과(특성화고 계열)가 47,625건으로 압도적 비중이다. 이 앱 사용자(동아공고)는 실제로 전문교과가 필요할 가능성이 있지만, 일반고 학교라면 3,124건(공통·일반선택 등)이면 충분하다. 처음부터 다 가져올지 범위를 좁힐지 정해야 시트/저장 방식 설계가 갈린다.

3.5. 추가 조사 — 교육부 고시 원문(hwp/hwpx) 직접 검증

결론: DECK6를 쓸 이유가 없어졌다. 고시 원문을 직접 파싱하는 쪽이 모든 면에서 낫다. 아래는 실제로 파일을 열어 파싱까지 돌려본 결과다.

3.5-2. HWP도 변환 없이 바로 읽힌다

3.5-3. 파싱 실측 — 구조가 기계적으로 매우 깔끔하다

최종 파서로 별책34를 다시 계측한 결과 숫자로 시작하는 전문교과 코드까지 포함해 성취기준 5,827개를 추출했다. 문서 구조가 아래처럼 규칙적이라 정규식 수준으로 처리된다.

주의 1 — 성취기준 코드 형식이 두 종류다

보통교과 (별책3·4)전문교과 (별책23~39)
형식[9국01-01] [12화언01-01]
[10공국1-01-01](공통과목은 과목명에 숫자 포함)		[성직 01-01] [의생 01-01-03]
(축약 2글자 + 공백 + 영역-요소-순서)
학교급 숫자있음 (9=중, 10·12=고)없음

파서를 하나로 뭉뚱그리면 놓친다. 실제로 처음에 좁은 정규식을 썼다가 공통국어1·공통수학1 등 공통과목 299개를 통째로 흘렸고, 패턴을 넓힌 뒤에야 1,792 → 2,091개로 복구됐다. 가장 많이 쓰이는 과목들이라 이 함정은 반드시 짚고 가야 한다.

뜻밖의 수확 — 전문교과 과목 카탈로그가 문서 안에 들어 있다

전문교과 별책 말미 【부록】 과목명 축약 글자에 17개 계열 전체의 과목 목록이 기준학과 | 과목군 | 과목명 | 축약글자 표로 실려 있다. 코드 접두어(성직)를 과목명(성공적인 직업 생활)으로 되돌리는 매핑표이자, 우리가 필요한 "학교급별 과목 드롭다운 목록" 그 자체다. 과목 목록을 따로 만들 필요가 없다.
