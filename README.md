# 학생 활동 기록 웹앱

교사가 학생 활동을 기록하는 Google Apps Script 웹앱이다. 학생 명단·증명사진은
관리자 소유 중앙 자료에 한 벌만 두고, 활동 기록은 교사 각자의 Drive에 각자 소유로
저장한다.

**설치는 [INSTALL.md](INSTALL.md)를 따른다.** 일반 사용자는 GitHub Release의
Windows 설치 도우미를, 개발자·AI 도구 사용자는 기존 clasp 방식을 선택할 수 있다.
이 문서는 구조·운영 계약·설정 항목을 설명한다.

**설치가 끝난 뒤 사용법은 아래 두 문서에 이미 있다. 새로 만들지 말고 그대로
안내한다.**

- 관리자(학생 명단·담당 승인 관리): [ADMIN_GUIDE.md](ADMIN_GUIDE.md)
- 교사(학생 활동 기록): [USER_GUIDE.md](USER_GUIDE.md)
- 위 둘을 목차·검색이 있는 한 페이지로 묶은 브라우저용 버전: [GUIDE.html](GUIDE.html)
  (파일을 내려받아 열거나, GitHub Pages를 켰다면 그 주소로 바로 연다. GitHub의
  저장소 화면에서 파일을 클릭하면 렌더링 없이 소스가 보인다 — 정상이다)

## 최신 버전: v1.2.0

- 설치 시 학교급(초등학교·중학교·고등학교)을 선택하고, 교육부 고시
  제2022-33호 각론 별책5~39 원문에서 생성한 해당 학교급 과목·성취기준을
  중앙 자료에 적재한다.
- 담당 신청과 관리자 담당 추가에서 과목명을 검색할 수 있다. 목록에 없는 과목은
  계속 직접 입력할 수 있고, 고등학교 계열은 제한이 아닌 검색 필터로만 쓴다.
- 활동 기록에서 담당 과목의 성취기준을 코드·문구로 검색해 선택할 수 있다.
  조회는 백그라운드에서 진행되어 학생 선택과 메모 입력을 막지 않는다.
- 자주 쓰는 성취기준을 수업별로 여러 개 고정·해제할 수 있다. 전문교과의 실제
  비고유 코드는 과목·영역·코드·원문 기반 내부키로 구분한다.
- 초등학교는 1~6학년, 중·고등학교는 기존대로 1~3학년을 허용한다.
- 기존 설치는 학교급을 설정하기 전까지 종전 기능을 그대로 사용한다. 새 기능을
  쓰려면 관리자 `연결 상태`에서 학교급과 성취기준 데이터를 한 번 설정한다.
- Windows용 portable 설치 도우미와 SHA-256 체크섬 생성 workflow를 추가한다.
  설치 도우미의 재시도 작업 폴더는 앱이 만든 관리 경로로만 제한한다.

전체 변경 이력은 [CHANGELOG.md](CHANGELOG.md)에 있다.

## 상태

- 구조: 중앙 학생·사진 읽기 + 사용자 소유 개인 활동기록 + 승인 시 중앙 자료 자동 공유·해지
- 코드·로컬 검사: 체크포인트 2.5 `91/91`, 체크포인트 2.6 `29/29`, 체크포인트 5 `87/87`,
  실행형 회귀 `65/65` 통과
- 실환경 사용: 학교 한 곳(학생 180명)에서 담당 신청·승인, 수강 그룹 편성, 활동
  기록 작성·수정·삭제, 공동교육과정 학생 추가·삭제까지 확인
- 아직 확인하지 못한 것: **해지할 때 중앙 자료 보기 권한이 실제로 제거되는지**.
  합성 교사 계정으로 확인이 필요하다. 제거에 실패하면 비활성 교사 행의
  `Drive 권한 제거 재시도`로 다시 시도할 수 있다.
- 외부 보안 감사는 받지 않았다.
- 변경 이력은 [CHANGELOG.md](CHANGELOG.md)를 본다.
- 개인 스프레드시트에는 `활동기록`, `활동기록보관`, `설정`, `삭제기록`만 만들며
  탭도 이 순서로 놓는다(교사가 파일을 직접 열었을 때 가장 자주 보는 순서다).
  학생 명단(`데이터베이스`)·`학생사진` 등 중앙으로 옮겨간 시트는 만들지 않는다.
- `활동기록`·`활동기록보관` 머리글:
  `기록ID, 기록일시, 학년, 반, 번호, 이름, 학적상태, 구분, 역량, 과목, 내용메모,
  작성자, 수정일시, 학생ID, 학년도, 담당키`
  마지막 `담당키`는 수강 그룹부터 채운다. 기존 시트는 접속할 때 열이 자동으로
  추가되며, 그 전에 쌓인 기록은 이 칸이 비어 있고 예전처럼 학년·반·과목으로
  담당을 판정한다.
- 교사 개인 Drive에 만드는 폴더와 파일 이름:
  `학교명_학생 활동 기록 데이터` 폴더 안에 `학교명_학생 활동 기록 데이터_<학년도>`
  스프레드시트가 학년도마다 하나씩 쌓인다. 폴더는 학년도로 나누지 않으므로
  이름에 연도를 붙이지 않는다. 학교 설치 전에는 학교명이 없어 예전 폴더 이름
  (`학생 활동 기록 웹앱 데이터`)을 쓴다. 이전 버전에서 만들어진 폴더는 이름을
  바꾸지 않으며, 저장된 폴더 ID로 계속 찾으므로 그대로 동작한다.
- 개인 Drive에 `사진_<학년도>` 폴더를 만들지 않는다. 증명사진은 중앙 폴더에서만
  읽는다. 이전 버전에서 만들어진 개인 사진 폴더와 시트는 자동 삭제하지 않으므로
  필요하면 소유자가 직접 정리한다.

## 중앙 자료 준비

관리자 중앙 스프레드시트는 다음 시트를 사용한다.

- `학생목록` 권장 헤더:
  `학생키, 학년도, 학년, 반, 번호, 이름, 학적상태, 사용, 생성일시, 수정일시`
- 또는 기존 v8.3 `데이터베이스` 호환 헤더:
  `학년, 반, 번호, 이름, 학적상태, 학생ID, 학년도`
- `사진정보` 권장(기존 v8.3 `학생사진`도 호환):
  `학생ID, 학년도, 사진키, 사진파일ID, 파일명, MIME유형, 파일수정일시, 동기화일시`
- `교사담당`:
  `담당키, 교사이메일, 학년도, 학년, 반, 과목, 담당유형, 사용, 생성일시, 수정일시`
- `담당신청`:
  `신청키, 교사이메일, 학년도, 학년, 반, 과목, 상태, 신청일시, 처리일시, 처리자, 처리사유, 담당키`
- `수강그룹`:
  `담당키, 그룹명, 생성일시, 수정일시`
- `수강그룹원`:
  `담당키, 학생키, 추가일시`
- `앱설정`:
  `항목, 값, 수정일시`

학교 설치 화면에서는 `새 중앙 자료 만들기` 또는 `기존 중앙 자료 다시 연결하기`를
선택한다. 새로 만들면 최초 관리자의 Drive에 중앙 스프레드시트와 사진 폴더를
생성하고, 다시 연결하면 입력한 기존 스프레드시트·폴더의 접근 권한을 서버에서
검증한 뒤 필요한 중앙 시트를 준비한다. 관리자 포털의 `중앙 시트 점검·생성`
버튼은 설치 후 누락된 시트를 다시 점검할 때 사용한다.
중앙 CSV 가져오기는 지정한 학년도의 명단만 교체하고 다른 학년도 행은 보존한다.

## Script Properties

새 프로젝트는 Apps Script 편집기에서 `registerInitialSchoolAdministrator` 함수를
한 번 실행한다. 웹앱 배포 전·후 모두 실행할 수 있지만, 스크립트 프로젝트의 편집
권한이 있는 계정만 최초 관리자로 등록된다. 이미 `ADMIN_EMAILS`가 설정된 기존
프로젝트는 그대로 호환된다.
등록 후 웹앱의 학교 설치 화면에서 학교명을 입력하고 새 자료 생성 또는 기존 자료
재연결을 선택하면 아래 속성이 저장된다. 기존 프로젝트의 수동 설정값도 계속
호환된다.

| 키 | 값 |
|---|---|
| `CENTRAL_DATABASE_FILE_ID` | 중앙 스프레드시트 ID |
| `CENTRAL_PHOTO_FOLDER_ID` | 중앙 사진 폴더 ID |
| `ADMIN_EMAILS` | 관리자 이메일, 쉼표·공백·줄바꿈 구분 |
| `STAFF_GROUP_EMAIL` | 선택 사항. 운영 메모용 Google 그룹 주소 |
| `ALLOWED_TEACHER_EMAILS` | 선택 사항. 담당 신청을 허용할 계정 목록 |
| `CENTRAL_SCHEMA_VERSION` | `4` |

`ALLOWED_TEACHER_EMAILS`는 **관리자 화면 `교사 관리` 탭 아래 `담당 신청 허용 범위`**
에서 설정한다. 이 속성을 직접 편집할 필요는 없다.

비워 두면(`제한 없음`, 기본값) 웹앱 URL을 아는 로그인 계정은 누구나 담당 신청을
할 수 있다. 승인 전에는 학생·사진에 접근하지 못하지만, 신청 자체는 관리자에게
알림 메일을 보내고 신청 이력을 남긴다.

`특정 도메인·계정만`을 고르면 목록에 없는 계정은 신청 단계에서 막힌다. 쉼표로
여러 개를 넣으며 `@학교도메인` 형태와 개별 이메일을 함께 쓸 수 있다.

```text
ALLOWED_TEACHER_EMAILS = @dongah.hs.kr, kim@gmail.com
```

`@gmail.com` `@naver.com` 처럼 **누구나 주소를 만들 수 있는 공용 메일 도메인은
통째로 지정할 수 없다.** 제한이 아니라 전 세계에 열어 주는 셈이 되기 때문이다.
같은 이유로 관리자 계정이 공용 메일이면 `내 도메인 넣기` 버튼이 나타나지 않는다.
개별 이메일(`kim@gmail.com`)은 사람이 특정되므로 막지 않는다.

Google Workspace 학교든 학교가 직접 운영하는 메일서버든, 그 도메인의 주소를
아무나 만들 수 없다면 제한 효과는 같다. 둘을 구분할 필요는 없다. Workspace라면
배포 화면의 도메인 전용 접근을 함께 쓰면 더 확실하다.

잘못 켜서 교사 전원이 막혀도 관리자 화면은 그대로 열리므로(`requireAdmin_`가
따로 지킨다) 같은 자리에서 다시 끌 수 있다. 이미 승인된 담당은 영향받지 않는다.

실제 속성값을 HTML·문서·로그에 복사하지 않는다. 기존 v8.3 중앙 DB 속성은
읽기 호환되지만 새 키 사용을 권장한다. `STAFF_GROUP_EMAIL`은 운영 메모용이며
인증·관리자 판정에 사용하지 않는다. Google 그룹 없이 운영하면 비워 두어도 된다.

## 관리자 설치 작업

1. 전체 런타임 코드를 새 Apps Script 프로젝트에 복사한다.
2. Apps Script 편집기에서 `registerInitialSchoolAdministrator`를 한 번 실행한다.
3. 웹앱을 `웹 앱에 액세스하는 사용자`로 배포한다.
4. 관리자 계정으로 `/exec`에 접속해 학교명을 입력하고 새 중앙 자료 생성 또는
   기존 중앙 자료 재연결을 선택한다.
5. 중앙 스프레드시트와 사진 폴더는 비공개 상태로 유지하고 교사에게 수동 공유하지
   않는다. 관리자가 담당 신청을 승인하면 앱이 해당 Gmail 계정에 보기 권한을
   자동으로 부여한다.
6. 합성 교사 계정으로 담당 신청·승인·해지를 시험해 보기 권한이 각각 추가·제거되는지
   확인한다. 해지 후 권한 제거 실패가 표시되면 비활성 교사 행의
   `Drive 권한 제거 재시도`를 실행한다.
7. 링크·그룹·도메인 공유는 개별 해지 후에도 접근을 남길 수 있으므로 사용하지 않는다.
8. 가능한 운영 환경에서는 학교 도메인의 로그인 사용자로 접근 대상을 제한하고,
   불가능하면 중앙 담당 미등록 계정 차단을 반드시 유지한다.

교사에게는 버전 배포된 `/exec` URL만 제공하고 Apps Script 프로젝트 편집
권한은 공유하지 않는다.

## 새 학년도 전환

학년도는 3월 1일에 저절로 넘어간다(3월 이후면 그 해). 별도 설정값이 아니므로
관리자가 바꾸는 것이 아니다. 넘어가는 순간 다음이 함께 일어난다.

- 지난 학년도 담당은 모든 교사의 목록에서 사라지고 접근도 거부된다
- 새 학년도 담당은 새 학년도 학생만 본다 (지난 학년도 명단과 섞이지 않는다)
- 교사 개인 DB는 `학교명_학생 활동 기록 데이터_<학년도>` 파일이 새로 만들어지고,
  지난 기록은 지난 학년도 파일에 그대로 남는다

관리자 포털 `연결 상태 → 새 학년도 시작하기`는 이 전환을 실행하는 버튼이 아니라
**준비 상태를 확인하고 지난 학년도 자료를 정리하는** 화면이다. 올해 학생·담당
건수를 보여 주고, 지난 학년도 학생 명단과 담당 설정을 항목별로 골라 비활성화한다
(삭제가 아니라 `사용` 열을 끄는 것이라 되돌릴 수 있다).

교사 개인 기록은 각 교사의 Drive에 있어 관리자가 접근할 수 없으므로 이 화면에서
건드리지 않는다. 담당이 끊긴 교사에게는 담당 수업 신청 화면에서 학년도가 바뀌었으니
다시 신청하라는 안내가 뜬다.

새 학년도에 관리자가 해야 할 일은 **새 학년도 학생 명단 업로드**와 **교사 담당
승인**뿐이다.

## 업데이트

새 버전이 나오면 **관리자 화면 `연결 상태` 탭 위쪽에 알림이 뜬다.** 링크를 누르면
무엇이 바뀌었는지 볼 수 있다.

확인은 브라우저가 GitHub 릴리스 목록을 직접 읽어서 한다. 서버(Apps Script)에서
읽으면 `외부 서비스 연결` 권한을 매니페스트에 넣어야 하고, 그러면 이미 쓰고 있는
교사 전원이 동의 화면을 다시 보게 되므로 그렇게 하지 않았다. 같은 이유로 교사
화면에서는 확인하지 않는다.

확인에 실패해도(저장소 접속 불가, 학교 망 차단 등) 화면에는 아무것도 뜨지 않으며
다른 기능에 영향을 주지 않는다.

적용은 수동이다. 릴리스 노트에 **어떤 파일을 바꿔야 하는지** 적혀 있으므로 그
파일만 Apps Script 편집기에 덮어쓰고 새 버전으로 다시 배포한다. 앞자리가 바뀐
릴리스(`1.x` → `2.0`)는 덮어쓰기 전에 릴리스 노트를 먼저 읽어야 한다.

## 비파괴 설치 초기화

관리자 포털의 `설치 설정 초기화`는 중앙 DB·사진 폴더 연결, 중앙 스키마 버전,
학교명과 설치 완료 상태를 초기화하고, 담당 수업 신청 이력도 함께 지운다.
신청 이력은 특정 중앙 `교사담당` 시트를 전제로 한 기록이라, 연결을 끊으면
`승인` 이력이 가리키던 담당 행을 찾을 수 없어 관리자 화면에는 승인으로 보이는데
담당 수업은 비어 있는 상태가 된다. 교사는 재연결 후 다시 신청하면 된다.

현재 관리자 목록, 교사 개인 DB·폴더와 기존 중앙 Drive 파일은 유지한다.
초기화 후 같은 관리자가 학교 설치 화면에서 새 중앙 자료를 만들거나 기존 중앙
자료의 링크를 다시 연결할 수 있다.

기존 중앙 파일은 Drive에 그대로 남으므로 실제 폐기가 필요하면 파일 소유자가
내용을 확인한 뒤 Drive에서 직접 처리한다.

## 최초 접근

```text
관리자
→ 서버 이메일로 ADMIN 판정
→ 관리자 포털
→ 필요 시 개인 이용자 모드
→ 관리자 개인 DB에 활동 기록

일반 교사
→ 서버 이메일로 USER 판정
→ 개인 저장소 생성/재사용
→ 학년도·학년·과목·여러 반 담당 신청
→ 관리자 승인 전까지 담당 접근 없음
→ 관리자 승인 후 중앙 교사담당에서 자기 담당 선택
→ 담당 학급 중앙 학생·사진 조회
→ 개인 DB에 활동 기록
```

관리자는 `학년 → 과목 → 반` 순서로 입력하며 `1, 2, 3`처럼 여러 반을 한 번에
등록할 수 있다. 교사 신청도 같은 방식으로 여러 반을 제출하며, 승인·거부 결과는
교사 화면에서 확인한다.

일반 교사에게 학생 CSV, 학교 전체 명단 작성, 관리자 비밀번호, 사진 묶음
업로드를 요구하지 않는다.

## 수강 그룹

고교학점제로 학급 단위 수업이 성립하지 않는 과목은 담당 신청에서 `수강 그룹`을
고르고 그룹 이름을 입력한다. 관리자가 승인하면 빈 그룹이 생긴다.

학생 편성은 **`내 담당 수업 신청` 탭 아래쪽 `수강 그룹 학생 편성`**에서 한다.
승인된 그룹이 없으면 이 영역은 나타나지 않는다. `편성할 수업` 드롭다운으로 어느
그룹을 다루는지 고르며, 목록에는 수강 그룹만 담기므로 학급 단위 수업은 선택할 수
없다. 체크 후 버튼으로 옮기거나 학생을 끌어다 놓을 수 있고, 목록마다 전체 선택
체크박스가 있다(후보 쪽은 이름으로 찾은 뒤 보이는 학생만 선택한다). `편성 저장`을
눌러야 반영된다. 활동 기록 탭의 수업 선택은 기록할 수업을 고르는 곳이지 명단을
고치는 곳이 아니라서 편성 화면을 두지 않았다.

편성 전인 그룹을 활동 기록 탭에서 고르면 학생 목록 자리에 편성이 필요하다는
안내가 뜬다.

그룹 담당의 반은 `0`으로 기록된다. `0반`은 실제로 없으므로 학급 단위 담당과
절대 겹치지 않는다. 화면에는 반 번호 대신 그룹 이름이 표시되며, 관리자 화면의
담당 신청 목록도 그룹 신청은 `0반` 대신 그룹 이름을 보여 준다.

수강 그룹은 여러 학년이 함께 듣는 경우가 흔하다. 담당 신청·수정 화면의
`함께 듣는 다른 학년`에 쉼표로 여러 학년을 입력할 수 있다. 기본 학년은
`교사담당` 시트의 `학년` 칸에 그대로 남고, 나머지는 `수강그룹` 시트의
**5번째 칸**(`추가학년`, `·`로 이어 적음)에 저장한다. 이 칸은
`CENTRAL_GROUP_HEADERS`(4칸)에 넣지 않았다 — 넣으면 이미 배포된 학교의
4칸짜리 `수강그룹` 시트가 전부 `CENTRAL_SCHEMA_INVALID`로 막히기 때문이다.
`centralHeadersMatch_`는 선언보다 열이 남는 것만 확인하므로 검증에는 걸리지
않고, 처음 값을 적을 때 머리글도 함께 채운다. 편성 후보는
`centralAssignmentGrades_`(기본 학년 + 추가 학년)로 판정한다.

관리자가 `교사 관리` 화면에서 수강 그룹을 다룰 때도 그룹 이름을 반드시
입력한다. 이름이 비면 화면에 `이름 없는 그룹`으로 표시되며, 그 행은 `수정`으로
이름을 채우거나 `삭제`로 정리한다. `삭제`는 담당 행과 함께 그 그룹의 이름·편성
명단(`수강그룹`·`수강그룹원`)까지 지운다. 교사가 이미 저장한 활동 기록은 각자
소유 파일에 있어 지워지지 않고, 중앙 자료 보기 권한 회수는 `해지` 버튼이 교사
단위로 따로 처리한다.

공동교육과정으로 들어온 타교생은 편성 화면의 `공동교육과정 학생 추가`로 넣는다.
학적상태는 `공동`, 반은 `0`, 번호는 99번부터 역순으로 배정된다. 실제 반에 넣으면
그 반 담임의 학생 목록에 모르는 학생이 나타나기 때문이다. 이 학생들도 중앙
학생목록에 남으므로 관리자가 확인·수정·비활성화할 수 있다.

잘못 넣었으면 편성 화면의 `공동교육과정 학생 삭제`로 교사가 직접 걷어낸다.
편성된 학생 목록에서 체크한 뒤 누르며, 다음 조건을 모두 만족할 때만 지워진다.

- 학적상태가 `공동`이고 반이 `0`인 학생 (우리 학교 학생은 지울 수 없다)
- 내 수강 그룹에 편성돼 있는 학생
- 다른 수강 그룹에는 편성돼 있지 않은 학생 (다른 교사의 명단을 깨지 않기 위해)

행을 지우는 것이 아니라 관리자 삭제와 같이 `사용`만 끄고 편성에서 뺀다. 이미
저장한 활동 기록은 학생 행을 참조하지 않으므로 그대로 남는다.

`위탁`은 우리 학교에서 밖으로 나간 학생이라 기록 대상이 아니다. `전학`·`자퇴`와
같이 목록에는 보이지만 선택할 수 없다.

## 사진 운영

사진명은 `학년 1자리 + 반 1자리 + 번호 2자리`를 사용한다. 예: 1학년 1반
1번은 `1101.jpg`. JPG·PNG·WebP, 512KB 이하의 미리 축소한 웹용 사진을
권장한다. 관리자가 중앙 폴더에 넣은 뒤 관리자 포털에서 동기화한다. 학생
명단은 사진 존재 여부만 먼저 받고, 실제 이미지는 화면에 보이는 카드부터
개별적으로 지연 로딩한다.

## 보안 한계

승인된 교사는 중앙 자료의 개별 보기 권한을 받으므로 앱 밖에서도 중앙 파일을 열 수
있다. 앱의 담당 학급 필터가 Drive 원본의 행·파일 접근까지 분리하지는 않는다.
링크·그룹·도메인 공유를 추가하면 앱의 개별 해지만으로 접근을 완전히 막을 수 없으므로
중앙 자료는 비공개 상태와 앱이 부여한 개별 보기 권한만 사용하는 것을 권장한다.

## 개인정보 관련 유의사항

교사가 학생 명단에 접근하는 일 자체는 나이스 등 기존 경로로도 이미 하고 있고,
학교가 학년 초에 받는 개인정보 제공·활용 동의로 다뤄진다. 이 앱이 새로 만드는
문제는 접근 권한이 아니라 **저장 위치**다 — 그 동의로 다뤄지는 자료가 학교 기관
계정이 아니라 교사 각자의 개인 Google 계정에 저장된다. 기존 동의 범위가 이런
비공식 저장소까지 포함하는지는 학교가 직접 확인해야 하고, 이 앱은 나이스를
대체하는 공식 기록 시스템이 아니라 교사 개인의 메모·초안 도구로 다루는 것을
권장한다.

이 저장소(코드)에는 실제 학생 개인정보가 들어 있지 않다. 개인정보는 설치 후
학교가 직접 연결하는 Google Drive(관리자 소유 중앙 자료, 교사 개인 소유 기록)에만
존재한다. 학생 명단·사진을 실제로 올리기 전에, 근무하는 시도교육청의 개인정보
취급 지침을 반드시 확인해야 한다.

## 로컬 검증

저장소 루트에서 실행한다. Node.js만 있으면 되고 Google 계정은 필요 없다.

```powershell
node .\verify-v8.4.js
node .\verify-v8.4-cp2.5.js
node .\verify-v8.4-cp2.6.js
node .\verify-v8.4-cp5.js
node .\verify-v8.4-runtime.js
```

`verify-v8.4.js`는 `.gs` 구문, 중복 함수, 매니페스트, 공개 함수 계약, 개인 기록
보존과 학생·사진의 중앙 이동을 검사한다. 통과하면 확인 문구 한 줄만 출력하고
종료 코드 0으로 끝난다.

체크포인트 회귀 검사기는 각각 `RESULT 91/91`, `29/29`, `87/87`를 출력한다.
`-cp2.6.js`가 `-cp2.5.js`를, `-cp5.js`가 `-cp2.6.js`를 안에서 다시 실행하므로
`-cp5.js` 하나만 돌려도 세 검사가 모두 수행된다.

`verify-v8.4-runtime.js`(`65/65`)는 `.gs`를 실제로 불러와 함수를 호출한다. 위
검사기들은 소스에 특정 문자열이 있는지만 보므로, 코드는 다 있는데 동작이 죽는
결함은 이 검사기만 잡는다.

로컬 통과는 Google 실환경 권한 통과를 의미하지 않는다.
